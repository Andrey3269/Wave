## 2. Что изменилось

### S2a — настройки интерфейса в SQLite (H3) и атомарная запись (N1)

**Проблема.** Громкость, последняя слышимая громкость, видимость текста, имя профиля и обложки миксов хранились только в localStorage окна. Он привязан к origin `http://127.0.0.1:<порт>`, а лаунчер берёт новый порт при каждом запуске (`launcher.py`, `backend.start()` с портом 0), поэтому значения терялись. `PUT /api/settings` применял ключи по очереди и при ошибке в одном оставлял остальные записанными (N1).

**Решение.**
- `GET /api/settings`: в `values` добавлены `volume`, `last_volume` (число 0…1), `lyrics_visible` (bool), `profile_name` (до 24 символов), `mix_covers` (объект `id микса → URL`); в ответ добавлен `meta.local_ui_migrated`. Прежние ключи `values` и `paths` не изменились.
- `PUT /api/settings`: сначала проверяются все ключи, затем всё пишется одной транзакцией (`library.transaction()`). `downloads_dir` проверяется записью на диск только после остальных ключей и применяется в памяти только после фиксации в базе. Любая ошибка → 400 без изменений.
- `POST /api/settings/migrate-local`: однократный перенос старых значений из localStorage. Один раз на профиль; пишутся только ключи интерфейса, которых ещё нет в базе; плохие значения пропускаются по одному; повторный вызов ничего не меняет.
- `GET /api/boot.js`: синхронный скрипт в `<head>`, ставит сохранённую тему до первой отрисовки. Прежний встроенный скрипт на localStorage остался запасным путём.
- Фронтенд берёт настройки из backend при старте, сохраняет изменения с паузой 400 мс (перетаскивание громкости — одна запись) и отправляет несохранённое при `pagehide`. Старые ключи localStorage читаются один раз для переноса и не удаляются (откат на прежнюю версию их найдёт).

**Совместимость.** API аддитивен. Одно уточнение: тело `PUT` теперь принимает любые JSON-значения, поэтому число в прежнем ключе (`{"theme": 5}`) даёт 400 «Недопустимое значение настройки.» вместо 422 от FastAPI. Фронтенд таких запросов не шлёт.

### S2b — состояние резолвера в lifespan (M1)

**Проблема.** Сторож лаунчера перезапускает uvicorn в том же процессе с новым event loop. Модульные `_resolve_sem`, `_inflight`, `_prefetching`, `_background` оставались от прежнего цикла: после конкуренции семафор был привязан к старому циклу, и резолвы падали с `RuntimeError` (500); ключи прогрева мёртвого цикла могли «залипнуть».

**Решение.** `stream.ResolverState` (семафор, задачи резолва, ключи прогрева, фоновые задачи) создаётся в lifespan (`app.state.resolver`) и закрывается при остановке: незавершённые задачи отменяются и дожидаются, наборы очищаются. `check()` с понятной ошибкой отказывает при использовании из другого цикла или после закрытия. Функции резолвера и прокси получают состояние явно; загрузки передают `request.app.state.resolver`. Ссылки (`_cache`) и прогретые «головы» (`_heads`) — данные процесса, они по-прежнему переживают перезапуск. Это не подавление `RuntimeError`, а смена владельца состояния.

### S2c — честный статус рекомендаций (M4)

**Проблема.** Любой сбой источников превращался в `200 {"tracks": []}`; интерфейс писал «Пока нечего предложить». `personalized` был `true` уже при наличии текущего трека или любой истории.

**Решение.**
- В ответ `/api/recommendations` добавлены `failed_sources` и `source_status` (`ok | partial | failed` по каждому опрошенному источнику) и `radio`. Различимы четыре исхода: есть результаты; источник ответил, но подходящего нет; частичный сбой; полный сбой.
- `personalized` = в выдаче есть трек, найденный поиском по любимому или слушанному артисту или получивший за него балл. `radio` = в выдаче есть трек из «радио» текущего трека. Логика рейтинга не менялась.
- Фронтенд: пусто + `failed_sources` — ошибка «Источник сейчас недоступен: YouTube Music» в баннере и в блоке под лентой с кнопкой «Повторить»; есть треки + сбой — пометка о неполной подборке; «Пока нечего предложить» — только при настоящем пустом ответе. То же правило — для бесконечной ленты, миксов, похожих треков и продолжения очереди.

### S2d — понятные ошибки стриминга (L6)

**Проблема.** Почти любой сбой yt-dlp, включая обычное отсутствие сети, давал «Не удалось получить поток (проверьте yt-dlp/куки)».

**Решение.** Ошибки резолвера и прокси разделены по причинам; тип уходит в заголовке `X-Wave-Error`:

| Причина | Код | Тип | Текст (смысл) |
|---|---|---|---|
| нет сети (DNS, отказ соединения, таймаут, TLS; в том числе формулировки Windows) | 503 | `network` | «Нет связи с YouTube Music. Проверьте подключение к интернету.» |
| YouTube просит подтвердить «не бот» | 503 | `bot_check` | единственный случай с упоминанием cookies (`YTDLP_COOKIES`); если файл задан — «возможно, устарел» |
| HTTP 429 | 503 | `rate_limited` | повторить через несколько минут |
| сбой прокси при заданном `YTDLP_PROXY` | 502 | `proxy` | «проверьте прокси», без адреса и учётных данных |
| «Requested format is not available», nsig и т. п. | 502 | `extractor` | формат изменился или yt-dlp устарел (раньше — «Трек недоступен», 404) |
| трек удалён, приватный, недоступен | 404 | `unavailable` | «Трек недоступен» |
| возрастное ограничение | 403 | `age_restricted` | как раньше |
| CDN дважды не соединяется | 503 | `network` | «Нет связи с сервером аудио …» |
| ссылка отклонена даже после обновления | 502 | `link_unavailable` | с кодом HTTP, без адреса ссылки |
| прочий ответ CDN | 502 | `upstream_status` | с кодом HTTP |
| прочее | 502 | `resolve_failed` / `internal` | без текста исключения |

В текстах для пользователя нет текста исключений, URL, подписей, путей, адресов прокси и расположения файла cookies; подробности — только в журнале.

### S2e — честные названия подборок (M13)

- «Моя волна» убрана отовсюду (баннер, `aria-label`, подписи очереди, подсказки, комментарии). Подпись ленты следует ответу API: «Подобрано по вашей истории» (`personalized=true`), «Похоже на текущий трек» (`radio=true`), «С чего начать» (нет истории и избранного), иначе «Подборка».
- «Слушать волну» → «Слушать подборку». «Под твою волну» → «Миксы по вашим трекам», только если в ряду есть радио по истории или избранному, иначе «Тематические миксы».
- «Открытия недели» → «Новинки 2026» (год текущий) с подписью «Поиск по запросу «новинки 2026»»; «Встряхнуть мою волну» → «Другая подборка · Новая выборка из рекомендаций». `id` миксов не менялись, сохранённые обложки работают.
- Условие готовности e2e переведено на `#hero[data-feed=ready]` в том же коммите.

## 7. Ограничения и риски

1. **WebView2 не проверялся.** Перенос из localStorage в реальном приложении сработает только на том origin, где старые значения лежат (порт меняется при каждом запуске). Первый запуск новой версии переносит то, что есть на его порту, и закрывает перенос; значения с других портов не переносятся намеренно, чтобы устаревшие данные не затирали новые.
2. **Сохранение при закрытии окна.** Несохранённые за последние 400 мс изменения отправляются при `pagehide` с `keepalive`. Получит ли их backend при закрытии окна PyWebView до остановки сервера, проверяется только в WIN-5.
3. **Тексты ошибок yt-dlp** классифицируются по подстрокам сообщений. Набор взят из реальных формулировок; новая формулировка после обновления yt-dlp попадёт в общий случай `resolve_failed` (без упоминания cookies). Проверка на живых источниках — LIVE-2/3 в S3.
4. **Тексты интерфейса S2e** утверждены владельцем 2026-10-13.
5. **Задачи загрузок** (`downloads._background`) по-прежнему модульные; их жизненный цикл, отмена и остановка — этап S11.
6. **Нестабильная проверка на Windows в CI (обнаружено после приёмки, 2026-10-13).** Запуск [38348939401](https://github.com/Andrey3269/Wave/actions/runs/38348939401) на `84ad223` (только документация; код совпадает с `4df5b50`, где CI зелёный): попытка 1 — `checks (windows-latest)` FAIL, шаг «Run all checks», код выхода 1 (то есть FAIL, не BLOCKED); Linux и `windows-build` — PASS. Попытка 2 того же коммита — все job'ы PASS. Локально (Linux) после этого: e2e через раннер 3/3 PASS, pytest 5/5 PASS. Какая проверка упала — **не установлено**: журналы GitHub Actions из облачной среды недоступны (хранилище логов отвечает 403). Подозрения без подтверждения: тайминги новых e2e-фаз S2 на медленном раннере Windows (пауза записи настроек 400 мс и ожидание 900 мс в `e2e_settings.py set`, перезапуск backend на другом порту) или тесты с реальными потоками и задержками (`test_stream_lifespan.py`). Проверки не ослаблены и не помечены как нестабильные. Что нужно: владельцу открыть журнал попытки 1 в веб-интерфейсе GitHub Actions и найти строку `FAIL`; исправление — отдельной задачей.
