## 3. Изменённое поведение

### 3.1. Перемешивание без повторов и «Назад» по истории (`0a65c1a`)

`Queue` расширена, а не заменена. У каждой позиции очереди — внутренний uid, поэтому история и круг перемешивания переживают перестановки, удаление и дубликаты одного трека.

- **Круг.** Следующий трек выбирается только из не сыгранных в текущем круге. Круг сыгран: при `repeat "all"` начинается новый, причём первым не становится только что игравший трек (если в очереди есть другие); иначе очередь закончилась (дальше — «Продолжать похожими», если включено, или остановка).
- **История.** uid в фактическом порядке воспроизведения и курсор. «Назад» при перемешивании идёт по истории; «Следующий» после «Назад» сначала проходит уже сыгранное «будущее» (тот же трек дважды подряд не играет), потом выбирает новый. Прямой выбор трека (клик в очереди) обрезает «будущее».
- **Шаг по истории явный**: его предлагают `nextIndex()`/`prevIndex()`, `select()` применяет его только к тому же треку. Это закрыло два дефекта, найденных тестами при разработке: случайный выбор, совпавший с предыдущей записью истории, принимался за «Назад», а устаревшее предложение `prevIndex()` применялось к следующему случайному выбору — в обоих случаях трек мог повториться.
- **Устойчивость выбора.** Случайный выбор запоминается, пока он допустим, — `nextIndex()` и `peekNext()` отвечают одинаково. Поэтому прогрев следующего трека теперь работает и при перемешивании (раньше при shuffle он отключался).
- Удаление, очистка, замена очереди согласованно очищают историю и круг; включение перемешивания начинает новый круг с текущего трека; основной порядок очереди не меняется никогда. Без перемешивания «Назад» — как в S9, предыдущий по порядку.

### 3.2. Повтор off / all / one (`0a65c1a`)

- `state.repeat` — `"off" | "all" | "one"` (было булево «повторять трек»). Кнопка: выкл → вся очередь → текущий трек → выкл. На всех трёх кнопках (мини-плеер, страница трека, полноэкранный плеер): `aria-pressed` (нажата при all/one), `aria-label` и `title` с названием режима («Повтор: выключен / вся очередь / текущий трек»), `data-mode`; повтор трека — значок `i-repeat-one` (тот же значок с «1»), подсветка — прежняя.
- `audio.loop` больше не используется: с ним не приходит `ended`, а повтор должен одинаково работать для файла и HLS и считаться новым прослушиванием. Повтор трека — в обработчике `ended`: тот же `<audio>`, тот же поток (для HLS — тот же сеанс hls.js, без нового `/playback`). «Следующий» при повторе трека переключает трек, как обычно.
- `repeat "all"` без перемешивания: после последнего трека — первый; очередь из одного трека повторяется.
- «Назад»: после 3 с — начало трека; иначе — предыдущая позиция модели; в начале истории/очереди — начало трека.

### 3.3. Восстановление очереди и позиции после перезапуска (`c644771`)

**Решение о хранении.** Сравнивались варианты из ROADMAP:

| | Строка в таблице `settings` (выбрано) | Отдельная таблица |
|---|---|---|
| Схема базы | не меняется (v1) | новая версия v2 и миграция с резервной копией |
| Откат на сборку до S10 | работает: S9 эту строку не читает | **не запускается**: база с `user_version` больше известной не открывается (защита S6) |
| Риск для данных | только одна новая строка | миграция всей базы |
| Изоляция от настроек | отдельный эндпоинт; `/api/settings` строку не показывает и не меняет (неизвестный ключ — 400, как раньше), при чтении настроек пропускает | естественная |

Решающим оказался откат: владелец переустанавливает сборки поверх друг друга (S4–S9), и база v2 сделала бы прежнюю сборку незапускаемой. Хранение — JSON-строка `playback_state`; ORM, новые СУБД и зависимости не вводились.

**API (аддитивно):** `GET/PUT/DELETE /api/player/state`, `PATCH` — только позиция (`{key, index, position}`; 409, если сохранённая очередь уже другая), `POST /api/player/state` и `/position` — для `navigator.sendBeacon`. Адрес выбран так, чтобы не путаться с `/api/stream/{source}/{id}/playback` (первоначальное имя `/api/playback` попадало под фильтры HLS-тестов S8, считавших такие запросы).

**Проверки (запись — 400 с сохранением прежнего, чтение — «состояния нет» и запись в журнал):** не больше 500 треков и 1 МБ (413), типы и диапазоны индексов, позиции, истории, курсора и круга, режимы; адрес потока всегда вычисляет сервер (`/api/stream/{source}/{id}`); обложка — только `https://` или `/api/local/…`, публичная ссылка — только `https://` на сайтах источников; управляющие символы обезвреживаются; неизвестные поля отбрасываются. Испорченная, неполная или «чужая» строка не роняет запуск. Длинная очередь сохраняется окном из 500 треков вокруг текущего.

**Частота записи (не на каждый `timeupdate`):** очередь, текущий трек, режимы — одним PUT через 0,8 с после последнего изменения, но не позже 3 с после первого (без этой границы быстрое листание откладывало запись бесконечно — найдено e2e); позиция — PATCH раз в 10 с во время игры, на паузе и после перемотки; при закрытии окна несохранённое уходит через `sendBeacon` (обычный `fetch` при выгрузке обрывается; запасной путь — `fetch keepalive`). До чтения сохранённого при запуске ничего не пишется; само восстановление ничего не пишет.

**Решение продукта о запуске: звук сам не включается.** После первого экрана восстанавливаются очередь (порядок, подпись, история «Назад», круг перемешивания), текущий трек, позиция и режимы. Трек показан на паузе с сохранённой позицией: мини-плеер, баннер главной с кнопкой «Продолжить», метаданные Media Session и состояние «пауза»; поток даже не запрашивается. Play (кнопка, баннер, медиаклавиша) продолжает с сохранённой позиции; перемотка до Play меняет позицию старта. Лента главной при запуске собирается как раньше (восстановление идёт после её запроса, иначе лента стала бы «похоже на» восстановленный трек). Если пользователь успел сам что-то запустить, сохранённое не применяется. Восстановленная очередь — «собственная»: продолжения из источника (подгрузки страниц) у неё нет.

### 3.4. История прослушивания и пропуски (`d8dc16d`)

Было: `POST /api/history` в начале каждого трека (запуск на секунду — «прослушивание»); пропуск — позиция меньше `min(30 с, 40 %)` при переключении; `/api/history/skip` помечал последнюю запись о треке.

Стало (`player/listen.js`):
- запись — **один раз за запуск**, когда **фактически проиграно** `min(30 с, 50 % длительности)`; длительность — реальная из `<audio>`, пока её нет — из метаданных; **неизвестная, нулевая или бесконечная — порог 30 с**;
- проигранное время копится только из приращений позиции, не больших прошедшего времени × скорость + 1 с, и после `seeking` отсчитывается заново: перемотка вперёд порог не обходит, перемотка назад, пауза и продолжение второй записи не дают, ускорение учитывается;
- пропуск — запуск, прерванный пользователем после начала звука и до порога; сигнал один, для прерванного трека; естественный конец, «Продолжать похожими» и ошибка потока — не пропуск. Прерванный трек берётся из самого запуска, поэтому исправление S9 («не трек нового списка») теперь следует из устройства, а у `playIndex` больше нет параметра `prev`;
- повтор трека — новый запуск: свой порог, одна запись за каждый проигрыш.

Backend: `/api/history/skip` со снимком `track` добавляет **отдельную** запись `skipped = 1` (с обрезкой до лимита, одной транзакцией). Помечать последнюю запись больше нельзя: короткий запуск не записывается, и пометилось бы прежнее полноценное прослушивание. Без `track` — прежнее поведение (тесты S1 сохранены); трек, не совпадающий с `source/id`, — 400. Страница «История» и рекомендации читают такие записи так же, как раньше (пропущенный запуск и раньше был записью `skipped = 1`). Отличие для пользователя: запуск, который не дошёл до порога и не был пропущен (пауза и закрытие, ошибка потока), в историю больше не попадает; порог пропуска сдвинулся с 40 % на 50 % и считается по проигранному времени.

### 3.5. «Открыть альбом» по ID (`cc2046f`)

- `Track.album_id` — новое **необязательное** поле. YouTube Music: ytmusicapi отдаёт у трека `album: {"name", "id"}`; id берётся, только если это browseId альбома (`MPRE…`) — id плейлистов (`OLAK5uy_…`, `VL…`) за альбом не выдаются; у треков страницы альбома — id этой страницы. SoundCloud: трек не ссылается на альбом (есть только `publisher_metadata.album_title`) — `album_id = None`, ничего не выдумывается.
- «Открыть альбом» открывает альбом по id, если он есть; иначе — как раньше, поиск по исполнителю и названию. Пункт меню показывается и у трека с id, но без названия альбома.
- **Совместимость/миграция:** старые клиенты поле игнорируют; снимки в избранном, истории и плейлистах до S10 его не имеют и открываются поиском; SQLite не меняется (снимки — JSON); `TrackIn` проверяет формат (422, как для остальных полей Track). Ожидания контрактных тестов обновлены с пометкой S10.

### 3.6. Нет соединения (`a4821cd`)

Было: событие `offline` открывало «Скачанные» (пользователь терял экран) и показывало тост. Стало: строка во всю ширину закреплённой верхней панели (`role="status"`) — «Нет подключения к интернету. Скачанные треки доступны.», кнопка «Скачанные» (общий обработчик `data-view`) и «Скрыть». Экран, плеер и очередь не трогаются; сообщение скрывается только по событию `online` браузера (или кнопкой «Скрыть»); повторные события переключают один и тот же элемент, обработчики регистрируются один раз. Запуск без сети по-прежнему открывает «Скачанные» первым экраном (терять нечего) и теперь показывает сообщение. Стиль — существующие токены и класс кнопки.

### 3.7. Media Session (WIN-11)

Регистрация не менялась: Play, Pause, Previous, Next, Seek Backward/Forward (по умолчанию 10 с), Seek To, Stop; метаданные (название, исполнитель, альбом, обложка) и `playbackState`. Изменено в связи с S10: Play/Seek/Stop работают и для восстановленного, ещё не запущенного трека (Play продолжает с сохранённой позиции, перемотка меняет позицию старта); `setPositionState` берёт позицию восстановленного трека; Previous/Next идут через модель (история перемешивания, повтор); после восстановления — метаданные трека и «пауза»; конец очереди — «пауза».

### 3.8. Посторонние исправления (коммиты 2, 3)

- `CircuitBreaker.remaining()` ограничен `cooldown` (погрешность float при неизменных часах).
- Запуск интерфейса больше не перетирает экран и источник, выбранные пользователем, пока шли запросы настроек и избранного (`boot()` открывает первый экран, только если никакой экран ещё не открыт; источник по умолчанию применяется, пока пользователь не выбрал свой). Для пользователя: поиск, начатый в первые секунды запуска, больше не выбрасывает на главную.

## 4. Архитектура

- `player/queue.js` по-прежнему без DOM (TARGET_ARCHITECTURE §11): history, cursor, round и modes — часть модели, а не DOM-обработчиков; наружу — `nextIndex({shuffle, repeat, auto})`, `prevIndex({shuffle})`, `peekNext(modes)`, `restartCycle()`, `serialize({max})`, `restore(snap)`, `onChange`.
- `player/listen.js` — без DOM. `player/persist.js` — единственное место, которое пишет `/api/player/state`.
- Граф модулей (`tests/js/modules.test.mjs`): новые модули достижимы из `main.js`, циклов нет (`persist` не импортирует `sliders` и `controller`: позицию для ползунков даёт `persist.currentPosition()`).
- Контракты API только дополнены: `/api/player/state*`, поле `album_id`, поле `track` в `/api/history/skip`.
