## 2. Как был устроен путь воспроизведения и что в нём мешало

**Путь (не менялся по сути).** `<audio>` → `GET /api/stream/yt/{id}` (`backend/stream.py`) → `_resolve` (кэш ссылок, один резолв на трек через `ResolverState.inflight`) → `_extract_sync` в пуле из 4 потоков, в каждом свой `YoutubeDL(ydl_opts(...))` → прямая ссылка googlevideo → проксирование с Range (206/200/416), перерезолв при 401/403/404/410. `ydl_opts()` общий с поиском SoundCloud.

**Причины проблем (подтверждены по коду yt-dlp 2026.8.19 и исходникам Deno 2.9.7):**

1. **H1.** В зависимостях голый `yt-dlp`: пакет `yt-dlp-ejs` не ставился, а `collect_all("yt_dlp_ejs")` в `wave.spec` молча пропускался. `js_runtimes` не передавался.
2. **yt-dlp-ejs обязателен.** В yt-dlp 2026.8.19 встроен только `yt.solver.core.js`; lib-скрипта (`yt.solver.lib.js`) в пакете нет, а запасной `yt.solver.deno.lib.js` требует загрузки npm-пакетов, которую Wave не разрешает. Без ejs Deno не решит задачи без сети.
3. **Поиск Deno самим yt-dlp.** Без явного пути yt-dlp в собранном exe ищет `deno` рядом с exe, **в текущем каталоге** и в `PATH` (`yt_dlp/utils/_jsruntime.py:_find_exe`) — непредсказуемо и небезопасно.
4. **Тихая деградация.** Без runtime yt-dlp переходит на JS-less клиенты с предупреждением, а `no_warnings=True` его отбрасывал: при сбое пользователь получал бы общую ошибку без указания причины, в журнале её тоже не было. Какой именно будет деградация на настоящем YouTube, фиксирует LIVE-4 (не выполнен, §9).
5. **L8 и зависания.** yt-dlp запускает `deno run … -` через `Popen.communicate_or_kill(stdin)` **без таймаута**: зависший процесс навсегда занимал поток резолвера (их 4). `launcher.py` выходит через `os._exit`, который на Windows не завершает дочерние процессы; комментарий «дочерних процессов нет» устарел.
6. **Окружение Deno.** По умолчанию Deno пишет кэш в общий `%LOCALAPPDATA%\deno` и в фоне ходит в сеть за обновлениями; переменная отключения — `DENO_NO_UPDATE_CHECK` (`cli/tools/upgrade.rs`), в задании — сокращённо `NO_UPDATE_CHECK`.

## 4. Получение Deno и проверка хэша

- `packaging/runtime/deno.lock` (JSON): версия, дата выпуска, страница релиза, для `windows-x86_64` и `linux-x86_64` — официальный URL `github.com/denoland/deno/releases/download/v2.9.7/…zip`, размер и SHA-256 архива, имя, размер и SHA-256 исполняемого файла внутри архива.
- Значения реальные: архивы скачаны 2026-10-13, SHA-256 совпал с официальными файлами `<url>.sha256sum` релиза (Windows `a0c3101b…2238`, Linux `c6527f24…3490`); хэши исполняемых файлов посчитаны из проверенных архивов (Windows `e020f3e2…9b33`, Linux `ce6a052b…1f21`).
- `packaging/fetch_runtime.py` (только стандартная библиотека): проверяет lock (официальный URL той же версии, хэши 64 hex, имя файла без путей), скачивает во временный `.part`, **сверяет SHA-256 до распаковки**, извлекает только нужный файл во временный файл, сверяет его SHA-256 и размер, атомарно заменяет, пишет метку. Ошибки: 2 — загрузка, 3 — хэш, 4 — неполный или небезопасный lock (до любой загрузки), 5 — битый архив; частичные файлы удаляются; режима «без проверки» нет. Повторный запуск ничего не скачивает, если файл проверен; подменённый файл восстанавливается из проверенного архива. `--check` — проверка без сети (её использует `wave.spec`).
- Бинарники лежат в `packaging/runtime/deno/` и `packaging/runtime/downloads/` и в git не попадают (`.gitignore`, проверка `hygiene`).
- Проверено на настоящей сети: загрузка Windows- и Linux-архивов по lock, повторный запуск, `--check` — PASS (локально и в CI).

## 5. `backend/jsruntime.py` и интеграция с yt-dlp

- **Поиск:** `WAVE_JS_RUNTIME` (файл или папка; если задан — только он, без молчаливой подмены) → упакованный `resource_dir()/runtime/deno/deno.exe` → `deno` из `PATH` **только при запуске из исходников**. В собранном приложении системный Deno, текущий каталог и `PATH` не используются.
- **Проверка:** запуск `<путь> --version` тем же `Popen`, что у yt-dlp, без окна, таймаут 10 с; разбор `deno X.Y.Z…`; сравнение с 2.3.0. Коды проблем: `not_found`, `start_failed`, `timeout`, `bad_output`, `unsupported_version`. Удача кэшируется до конца работы, неудача перепроверяется не чаще раза в 60 с.
- **yt-dlp:** `ydl_opts()` всегда передаёт явный путь `{'deno': {'path': …}}`, а без пригодного runtime — пустой `js_runtimes` (иначе yt-dlp включил бы deno и искал бы его сам). Экземпляры `YoutubeDL` пересоздаются при смене runtime. Предупреждения yt-dlp идут в `wave.log` через логгер (повторы не чаще раза в 10 минут) вместо отбрасывания.
- **Окружение:** `DENO_DIR=<каталог данных>\deno`, `DENO_NO_UPDATE_CHECK=1` — в окружение процесса (yt-dlp передаёт Deno копию `os.environ`). Проверено на настоящем Deno: кэш пишется только в `DENO_DIR`, в том числе по пути с пробелами и кириллицей, в домашний каталог — ничего.
- **Ошибки для пользователя:** при сбое резолва YouTube с типом `extractor`, `resolve_failed` или `internal`: runtime непригоден → `503 js_runtime` («Компонент воспроизведения YouTube (Deno) не найден или повреждён. Переустановите приложение.» в сборке; в разработке — подсказка про Deno и `WAVE_JS_RUNTIME`); runtime в порядке, но yt-dlp сообщил о сбое решения JS-задачи → `502 js_runtime_failed`. Настоящие причины (удалён, приватный, нет сети, возраст, проверка на бота, лимит) называются как прежде. Если yt-dlp всё же получил поток в урезанном режиме, воспроизведение не блокируется. SoundCloud и скачанные треки не затронуты. Фронтенд не менялся: он уже показывает `detail` ответа (подтверждено e2e и скриншотом).
- Лаунчер при каждом запуске проверяет runtime в фоне и пишет в журнал `JS-runtime для yt-dlp: deno 2.9.7 (bundled, <app>\runtime\deno\deno.exe)` (требование WIN-6).

## 6. Deno в сборке PyInstaller

- `packaging/wave.spec` не собирает, пока `fetch_runtime.is_ready(lock, "windows-x86_64")` не подтвердит файл; кладёт `deno.exe` в `<_internal>\runtime\deno\` (там его ищет `jsruntime.bundled_path()` через `sys._MEIPASS`), `deno.lock` в `<_internal>\runtime\` (диагностика сверяет версию), `licenses\` в `<_internal>\licenses\`.
- `yt_dlp`, `yt_dlp_ejs`, `ytmusicapi`, `certifi` стали обязательными (раньше отсутствие молча пропускалось); сборка проверяет, что `.js` yt-dlp-ejs попали в `datas`.
- `build_windows.bat`: `fetch_runtime.py` перед PyInstaller, после — `start "" /wait dist\Wave\Wave.exe --diagnostics --output build\diagnostics.json`, при коде 1 сборка останавливается. Шаг установщика не менялся (S4).
- Проверено: локальная сборка PyInstaller на Linux (механика `datas`, запуск frozen-бинарника из `Мои программы/Волна Тест` и из `/`: упакованный runtime найден, версия из lock в сборке) и сборка Windows в CI (§9, §10).
- **Размер `dist\Wave` (CI, Windows):** 147,1 МБ, из них `runtime\deno` 92,9 МБ и `yt_dlp_ejs` 0,15 МБ; без добавлений S3 — 54,0 МБ (вычислено в той же сборке вычитанием: других изменений состава нет). Сжатый архив Deno — 42,6 МБ; влияние на размер установщика — S4.

**Лицензии** (`licenses/`, в сборке `_internal\licenses\`): Deno — MIT (текст из репозитория, тег `v2.9.7`); V8 15.0.245.2 — текст `LICENSE` из репозитория V8 (Deno 2.9.7 сообщает эту версию); yt-dlp и yt-dlp-ejs — Unlicense (из dist-info); meriyah 6.1.4 (ISC) и astring 1.9.0 (MIT), встроенные в yt-dlp-ejs, — `BUNDLED_DEPENDENCIES.txt` (тот же баннер стоит в `lib.min.js`); сводный `THIRD_PARTY_NOTICES.txt`. **Открытый вопрос:** официальный архив Deno не содержит сводных уведомлений для встроенных Rust-библиотек; их перечень определяется по `Cargo.lock` Deno v2.9.7. Это отмечено в `THIRD_PARTY_NOTICES.txt` и требует проверки перед публичным распространением (S4). Полный перечень лицензий всего дистрибутива (Python, pywebview и др.) — S4.

## 7. Диагностика

- **`GET /api/diagnostics`** (в рабочем потоке, без сети, ~0,2–0,7 с): версии приложения-окружения (frozen, Python, ОС), yt-dlp, yt-dlp-ejs (установлен, версия, читаются ли скрипты, совпадает ли с решателем), выбранный runtime и все проверенные кандидаты (источник, путь, версия, проблема), закреплённая версия, каталог кэша Deno и право записи, `cookies_configured`/`proxy_configured` (только да/нет), список проблем с важностью и подсказками. Пути — `<app>`, `<data>`, `~`. Поля `playback_verified=false` и `note` прямо говорят, что проверена конфигурация, а не воспроизведение. Версии самого приложения пока нет (`backend/version.py` — S4), поэтому поле не выдумывалось.
- **`Wave.exe --diagnostics [--live <videoId>] [--json] [--output <файл>]`** (`launcher.py`): без окна, без проверки WebView2 и единственного экземпляра (работает рядом с запущенным Wave), коды 0/1; неизвестные аргументы игнорируются, обычный запуск не изменился. Вывод: stdout → перенаправленный дескриптор → консоль родителя (оконный exe); надёжный путь — `--output` и код возврата. В режиме диагностики приложение **никогда не показывает модальных окон** (см. §10, CI). `--live` — явный режим с сетью: резолв тем же кодом, что у плеера, и один Range-запрос; в отчёте число решений JS-задач в Deno (`js_challenge_runs`), ссылка не выводится.
- Отсутствие yt-dlp-ejs или несовпадение версии — **критическая** проблема (см. §2.2).

## 8. Жизненный цикл процессов

- Обёртка над `yt_dlp.utils.Popen.__init__` (тот класс, через который `yt_dlp/extractor/youtube/jsc/_builtin/deno.py` запускает Deno): на Windows `CREATE_NO_WINDOW` (у консольного `deno.exe` нет окна, даже скрытого); каждый процесс учитывается.
- Сторож завершает процесс, работающий дольше 30 с (yt-dlp ждал бы бесконечно); `communicate` возвращается, резолв завершается ошибкой, поток пула освобождается.
- Windows Job Object с `KILL_ON_JOB_CLOSE`: дочерние процессы завершаются вместе с Wave при любом выходе (закрытие окна, `os._exit`, падение) — так устроен механизм Windows, закрытие задания проверено тестом на `windows-latest`; сценарий WIN-7 с окном приложения не выполнялся. Если привязка не удалась, это один раз пишется в журнал, остальные меры работают.
- Завершение всех дочерних процессов при остановке backend (lifespan, в том числе перезапуск сторожем) и в лаунчере перед `os._exit`; диагностика завершает их перед выходом.
- Модель стриминга и контракт `/api/stream` не менялись; `stream.py` изменён точечно (опции, логгер, классификация ошибок, пересоздание `YoutubeDL`).
