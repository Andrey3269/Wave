## 3. Изменённое поведение

**Изоляция (M2).**
- Вызовы ytmusicapi и API SoundCloud больше не идут через `asyncio.to_thread` (общий пул event loop). У каждого источника свой пул: YouTube Music — 4 потока + 8 в очереди, SoundCloud — 2 + 4. Сверх предела запрос сразу получает 502 «… не успевает отвечать: слишком много запросов ждут ответа» (`code: unavailable`, статус `degraded`), в очередь не встаёт.
- Настоящие таймауты HTTP: ytmusicapi — сессия requests с таймаутом 5 с на соединение и 10 с на чтение (было 30 с по умолчанию в библиотеке); SoundCloud — `socket_timeout` yt-dlp 7 с. По ним зависший поток завершается сам (проверено против молчащего локального сервера, §4).
- Таймаут ожидания — как до S7: поиск 6 с (`SEARCH_TIMEOUT`), каталог 25 с, рекомендации 12 с. По таймауту задача из очереди отменяется по-настоящему; уже работающий поток Python остановить нельзя — он помечается брошенным и занимает место в пуле, пока не завершится по таймауту HTTP. Поэтому брошенных задач не больше, чем потоков пула. То же при уходе клиента (отмена запроса).
- SoundCloud: вместо одного экземпляра yt-dlp под глобальной блокировкой (все запросы шли строго по одному, зависший держал остальные) — свой экземпляр в каждом потоке пула.
- При остановке backend задачи из очередей пулов отменяются.

**Cooldown (M3).** YouTube Music после сбоя — пауза 45 с (`YT_SOURCE_COOLDOWN`), SoundCloud — 300 с (`SOURCE_COOLDOWN`, как раньше). Пауза действует на все операции источника: поиск отвечает сразу результатами другого источника (`failed_sources`, `source_status: cooldown`), каталог — 502 «… временно недоступен после сбоя. Повторная попытка — примерно через N с.», рекомендации — сразу `failed`. Открывают паузу: нет связи, таймаут, лимит запросов, отказ в доступе к API — всегда; внутренняя ошибка и ограничение доступа — только при поиске. Не открывают: «не найдено», пустая выдача, переполнение пула, сбой разбора одной страницы, сбой необязательной части страницы. Успешный вызов снимает паузу. Изменение для SoundCloud: раньше пауза действовала только на поиск треков, теперь и на его каталог и рекомендации.

**Кэши (M9).** Поиск — 256 записей × 300 с (как раньше по размеру, вытеснение теперь LRU); страницы артистов — 32 × 600 с, неполная страница не кэшируется (раньше без лимита числа артистов, каждый до 500 «сырых» песен); тексты — 512 × 24 ч (раньше без лимита и срока). Прежняя семантика сохранена: нормализация запроса, неполные результаты поиска не кэшируются, «Очистить кэш» сбрасывает всё.

**Ошибки и статусы (аддитивно).**
- Ошибка источника: 502 (как раньше), `detail` теперь называет источник («YouTube Music не ответил вовремя. Попробуйте позже.»; было «Источник временно недоступен. Попробуйте позже.»), плюс `code` (тип), `source`, `source_status`.
- Поиск треков: при сбое единственного выбранного источника (так ищет фронтенд) `detail` — его причина; при нескольких — прежний текст «Источники поиска недоступны». Тело дополнено `code`, `failed_sources`, `source_status`.
- `source_status` в `/api/search`, `/api/search/{kind}`, `/api/artist/...`, `/api/album/...`: `ok`, `degraded`, `cooldown`, `disabled`. Рекомендации — без изменений (`ok | partial | failed`, S2).
- `GET /api/sources` (новый): статус, остаток паузы, тип последней ошибки, загрузка пула, возможности, участие в поиске. Без секретов и ссылок.
- Фронтенд не менялся: он уже показывает `detail` и недоступные источники из `failed_sources`.

**Совместимость.** `Track`, URL `/api/...`, `stream_url`, `failed_sources`, `has_more`, порядок и нормализация результатов, пагинация, `detail` — сохранены. Загрузки S5 (`download_policy.py`, `downloads.py`, формат файлов, индекс, офлайн-воспроизведение) и база S6 не затронуты. Новых зависимостей нет.

## 6. Таймауты, отмена, cooldown, кэши — кратко

| | YouTube Music | SoundCloud |
|---|---|---|
| Пул | 4 потока + 8 в очереди | 2 + 4 |
| Таймаут HTTP (настоящий) | 5 с соединение, 10 с чтение на запрос | 7 с `socket_timeout` на запрос |
| Ожидание | поиск 6 с, каталог 25 с, рекомендации 12 с | то же |
| Пауза после сбоя | 45 с | 300 с |
| Открывают паузу | нет связи, таймаут, лимит, отказ API; при поиске также внутренняя ошибка и ограничение доступа | то же |
| Не открывают | «не найдено», пустая выдача, переполнение пула, сбой одной страницы, необязательная часть страницы | то же |

Кэши: поиск 256 × 300 с, артисты 32 × 600 с, тексты 512 × 24 ч.

## 7. Риски и обязательные ручные проверки (Windows 11, владелец)

Риски:
- **N4 (новое): поток SoundCloud нестабилен.** В живой проверке SoundCloud отдавал прогрессивный mp3 лишь в 4 из 9 резолвов. Плеер принимает только прогрессивный поток, поэтому часть треков SoundCloud не играет и не скачивается, а пользователь видит неверную причину («изменил формат ответа / yt-dlp устарел»). Возможно, это особенность облачной сети; если повторится у вас — это задача S8 (повторный резолв, честное сообщение, оценка HLS).
- Пустые разделы песен и альбомов YouTube Music в облачной среде (LIVE-1 BLOCKED) — у вас LIVE-1 должен вернуть треки; если нет, это изменение у YouTube или ytmusicapi, а не S7.
- Короткая пауза YouTube Music (45 с) после случайного сбоя.
- Неофициальные интерфейсы обоих источников (M10, REPOSITORY_AUDIT §5).
- Брошенный поток доживает до таймаута HTTP (§5, M2).
