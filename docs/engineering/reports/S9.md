## 3. Изменённое поведение

Декомпозиция переносит код без изменений (кроме путей импорта, локальных имён `play` в двух построителях карточек и удалённого неиспользуемого псевдонима `flashStatus`). Видимых изменений два, оба намеренные:

### 3.1. M11 — очередь больше не делит массив со списком на экране (`298974b`)

Раньше `playFromList` делал `state.queue = state.list`: сортировка списка переставляла очередь, а «Следующий» играл следующую строку отсортированного списка. Теперь:

- у `Queue` собственный массив; `load()` копирует треки;
- `sortList()` меняет только список экрана;
- новая страница списка (`appendTracks`) или ленты главной (`loadMoreHome`) продолжает очередь явным `queue.extend()` через `continuation: () => Promise<Track[]>`, и только треками, которых ещё не было из этого источника;
- если очередь заменили, пока шёл запрос продолжения, ответ игнорируется.

Сохранено, как было: любая правка очереди пользователем (добавить, убрать, переставить, очистить) или дописанные похожие треки делают очередь собственной — связь с источником и продолжение снимаются (раньше первая правка копировала массив). Клик по играющей строке по-прежнему ставит паузу.

### 3.2. Сигнал «пропуск» отправляется для прерванного трека (`8efa23a`)

Найдено при разделении очереди. `playTracks`/`playFromList` заменяли очередь до того, как `playIndex()` читал текущий трек, — и `POST /api/history/skip` уходил для трека **нового** списка на **старой** позиции. Это отрицательный сигнал для рекомендаций по треку, который пользователь не пропускал, а пропущенный не учитывался. Теперь прерванный трек запоминается до замены очереди. Коммит отдельный: это исправление дефекта, а не перенос.

### 3.3. Не поведение, но заметно в сети

`Cache-Control: no-cache` для файлов интерфейса: браузер перепроверяет их по ETag (304 без тела). Нужно, чтобы после обновления приложения не смешались модули двух версий из кэша.

**`Queue`** (`player/queue.js`):

| Член | Назначение |
|---|---|
| `load(tracks, {label, source, continuation})` | новая очередь — копия треков; `source` — массив-источник (только для `isFrom`), `continuation: () => Promise<Track[]>` |
| `tracks` (копия), `length`, `index`, `current`, `at(i)`, `label` | чтение; изменить очередь можно только методами |
| `isFrom(source)` | «очередь играет мой список и не правилась» — для паузы по клику на играющую строку |
| `select(i)`, `nextIndex({shuffle})`, `prevIndex()`, `peekNext()` | навигация; перемешивание — случайный, но не текущий (как раньше) |
| `add(track, next = false)`, `remove(i)`, `move(i, d)`, `moveTo(from, to)`, `clear()`, `append(tracks)` | правки; текущий трек остаётся текущим; любая правка снимает связь с источником |
| `extend()` | запросить продолжение и дописать в конец только треки, которых из этого источника ещё не брали; если очередь за время запроса заменили или поправили — ничего не дописывает; повторные и параллельные вызовы дублей не дают |

`play(tracks, i)` загружает очередь как `queue.load(tracks, {source: tracks, continuation: async () => tracks})`: продолжение — явная функция, которая по запросу читает текущее содержимое списка экрана. Экран вызывает `queue.extend()` сам, когда к списку (`appendTracks`) или ленте главной (`loadMoreHome`) пришла новая страница и `queue.isFrom(...)` истинно. Очередь никогда не держит ссылку на массив экрана как на свои данные.

**Правила графа** (проверяются `tests/js/modules.test.mjs`): все импорты относительные и существуют; каждое импортируемое имя экспортируется; циклов нет; каждый файл `frontend/js` достижим из `main.js`; нет `import()` и загрузки скриптов из сети. Связь «экран → другой экран» идёт через `bus` или через функции, которые передаёт `main.js` (`initList({onArtist, onDownload})`, `initMenu(actions)`), а не прямым импортом.

**Сохранность.** Регистраций `addEventListener`: 82 до и 82 после (из них на `document` — 10 и 10). Атрибутов `data-do` в `index.html`: 16 и 16. `style.css` не менялся. Контракты API и форма `Track` не менялись (`trackPayload` закреплён `tests/js/api.test.mjs`).

**Отличия от списка TARGET_ARCHITECTURE §11.** Добавлены модули, которых нет в списке: `core/elements.js` (иначе каждый модуль заново искал бы одни и те же узлы), `state/mixes.js`, `components/favorites.js`, `lyrics.js`, `share.js`, `views/list.js`, `shell.js`, `sidebar.js`, `player-bar.js` — у этих частей `app.js` были самостоятельные данные и обработчики, и без отдельных модулей они либо снова собирались бы в монолит, либо давали циклы импорта. Возможности, которые §11 приписывает `queue.js` (shuffle без повторов с историей, repeat off/one/all в модели, сериализация), относятся к S10 и в S9 не добавлялись: поведение перемешивания и повтора сохранено как было.

### Отклонения от порядка шагов задания

1. **Переключение на `type="module"` — третьим коммитом, а не последним.** Пока `app.js` — классический скрипт, вынесенные модули не исполняются приложением, и e2e после каждого коммита не проверял бы их. Поэтому сначала `app.js` стал модулем (`4b1b565`: семантика выполнения та же, что у `defer`; модульный код всегда strict — директива `"use strict"` удалена), а на последнем шаге вход переключён на `js/main.js`. Масштаб — одна строка `index.html`.
2. **`FrontendFiles` до перехода на модули** (`2d2a64b`). `StaticFiles` берёт тип файла из `mimetypes`, а на Windows он читает реестр, где `.js` бывает записан как `text/plain`. Классический скрипт это терпит, модуль — нет: WebView2 не исполнит его, окно останется пустым. Без этого шаг 7 мог бы работать в CI и не работать на части машин. API, контракты и защита localhost не менялись (`tests/api/test_frontend_static.py`: на момент `2d2a64b` 7 из 8 тестов падали без исправления при подменённом реестре).
3. **Связанные компоненты** (`track-row`, `cards`, `menu`) вынесены после контроллера, а не вместе с диалогами: так требует §11 («`core` → `components/dialogs, toast` → `player/queue` → `player/controller` → `views`»), они зависят от `play()`.

## 7. Оставшиеся риски

1. **WebView2 не проверен.** Главное, что видно только в окне приложения на Windows, — загружаются ли модули. Защита: тип `.js` не зависит от реестра (`FrontendFiles`), сборка проверяет состав `frontend\js`, e2e в CI идёт против установленного `Wave.exe` с настоящим реестром раннера. Но это Chromium, а не WebView2. Нужен п. 1–4 чек-листа.
2. **Пустое окно при ошибке модуля.** Ошибка импорта или синтаксиса в любом модуле останавливает весь интерфейс (у классического скрипта упала бы одна функция). Граф и экспорт проверяются `modules.test.mjs`, синтаксис — `node --check`, но ошибка времени выполнения при инициализации даст пустое окно. Отдельного экрана «интерфейс не загрузился» нет — кандидат для S12/S16.
3. **Реальный звук.** CI и e2e используют подделку сети и не доказывают воспроизведение звука; S9 движок S8 не менял (перенос без изменений).
4. **Таймаут `test_hls_browser` на Windows** (§6) — нестабильный тест S8, один раз из нескольких прогонов. Если повторится — увеличить ожидание или найти гонку.
5. **`node --test tests/js`** в Node 21+ не работает (§5.1); правильная команда — в README и TEST_STRATEGY.
6. **Порядок дописанных треков.** Продолжение отдаёт текущее содержимое списка экрана, и новые треки страницы попадают в конец очереди в том порядке, в каком они стоят в списке (после сортировки — в отсортированном). Прежний порядок очереди при этом не меняется. Если в S10 понадобится порядок «как пришло из источника», это решается в функции продолжения, без изменения модели.
