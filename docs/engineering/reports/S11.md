## 3. Изменённое поведение

### 3.1. Единый менеджер загрузок, лимит и очередь

Вместо голого множества задач модуля — `DownloadManager` в `app.state.downloads`. Он создаётся и закрывается в lifespan: его объекты asyncio принадлежат циклу этого запуска (как резолвер, находка M1). Второго механизма нет: POST, отмена, остановка и очистка идут через него.

**Лимит — 2 одновременные загрузки** (`MAX_PARALLEL`). Задание предлагало 3, если в проекте нет утверждённого значения; значение есть — 2 записано в согласованном владельцем TARGET_ARCHITECTURE §9. Доводы за 2: каждая загрузка держит соединение с CDN и резолв yt-dlp; источники ограничивают частоту запросов (`rate_limited`, `bot_check`); две загрузки уже заполняют обычный домашний канал, третья скорее растягивает все три. Значение — одна константа; пользовательская настройка не добавлялась. Если владелец хочет 3 — это одна строка и один тест.

- Лимит охватывает всё от `preparing` (резолв) до записи в индекс, а не только создание задачи.
- Сверх лимита задача получает новое состояние **`queued`** и ждёт; место передаётся ожидающему по порядку (FIFO) и освобождается при любом исходе: успех, ошибка, отмена, отмена до первого шага задачи.
- Повторный POST того же трека, пока его задача жива (в любом состоянии, включая `queued` и финальную уборку), возвращает ту же задачу.
- POST во время остановки приложения — 503, `X-Wave-Error: shutting_down`.

### 3.2. Отмена

`DELETE /api/downloads/jobs/{source}/{id}` — аддитивный маршрут; удаление готовой копии — прежний `DELETE /api/downloads/{source}/{id}` (4 и 2 сегмента пути — конфликта нет; оба проверяют источник и id прежним `_check`).

- Отмена ждёт, пока задача закроет файл, удалит свою `.part` и освободит место. Ответ — итог: `cancelled` (`error: null`, `code: "cancelled"`); `done`, если трек уже фиксируется; прежняя ошибка, если задача успела ей закончиться. Повторная отмена — тот же итог. Нет задачи — 404, `X-Wave-Error: no_job`.
- Новое терминальное состояние `cancelled` — не ошибка источника и не успех. Остановка приложения даёт `code: "shutdown"`.
- **Точка фиксации** (`_Commit`): удаление старой неиндексированной папки, `os.replace` временной папки и запись строки SQLite — одна операция в потоке. Отмена, пришедшая в этот момент, получает `done`: не бывает ни полуперенесённой папки, ни строки индекса без файлов.
- Итог задачи публикуется **после** удаления `.part`: повтор того же трека не может начать писать в папку, которую старая задача ещё удаляет.
- Реальные точки отмены, покрытые тестами: ожидание в очереди, резолв (общий, под `shield` — отмена загрузки не прерывает резолв для плеера), передача аудио, запись в потоке, обработка (обложка, текст), запись `metadata.json` перед фиксацией, сама фиксация, финальная уборка, повторная отмена в окне между завершением задачи и её колбэком.

### 3.3. Запись вне event loop

Аудио (прогрессивный поток и HLS), обложка, `lyrics.json`, `metadata.json`, перенос и удаление папок — в потоках (`asyncio.to_thread` через `download_io.run_in_thread`).

- Отмена coroutine не останавливает уже идущий вызов в потоке. Поэтому `run_in_thread` при отмене **дожидается конца этой операции** и только потом пробрасывает отмену; следующая операция не начинается. Ждём сам поток, а не asyncio-обёртку: при остановке цикла `asyncio.run` отменяет и обёртку, но запись всё равно доводится до конца до закрытия файла.
- Файл и папку закрывает и удаляет одна операция в потоке (`remove_partial`) — после конца любой записи. Поздняя запись не может ни попасть в закрытый дескриптор, ни заново создать удалённую `.part`.
- Прогрессивный поток пишется пачками до `WRITE_BATCH` = 1 МБ; всё полученное до обрыва CDN записывается до следующего Range-запроса — продолжение с первого недостающего байта (N2, S8) не теряет и не дублирует байты. Логика Range не менялась.
- Доказано тестами: запись идёт не в потоке event loop; пока запись «висит», backend отвечает на запросы; в памяти копится не больше `WRITE_BATCH` + один сетевой чанк.

### 3.4. Очистка `.part` при старте во всех корнях

Раньше `cleanup_partial()` смотрела только в текущий `downloads_dir()`. Теперь корни:

1. текущий каталог загрузок (настройки или `WAVE_DOWNLOADS_DIR`);
2. каталог по умолчанию `~/Downloads/Wave` — только при обычном запуске (без `WAVE_DATA_DIR` и `WAVE_DOWNLOADS_DIR`; тесты, e2e и отладка не трогают настоящую папку пользователя);
3. каталоги из индекса SQLite, в которых Wave действительно сохранял треки — `library.verified_roots`. Строки базы не доверенные (N3): каталог засчитывается, только если источник и id допустимы по правилам POST, строка проходит проверки чтения, имя папки оканчивается на «[источник-id]» этого трека и в папке лежат аудиофайл и `metadata.json`. Строка на `C:\Windows` или на «Фото [2020-лето]» каталогом загрузок не становится; доступность каталога проверяется один раз на каталог.

Удаляются только папки прямо в корне, чьё имя совпадает с шаблоном загрузчика `… [yt-<11 символов>].part` / `… [sc-<цифры>].part`. Ссылки (symlink и Windows junction — по тегу reparse point; плейсхолдеры OneDrive ссылками не считаются) не обходятся и не удаляются. Внутри `.part` удаляются только файлы и ссылки, без рекурсии; чужой подкаталог оставляет папку на месте. На POSIX удаление идёт относительно открытого дескриптора каталога (`O_NOFOLLOW`, сверка `samestat`), на Windows — с повторной сверкой каталога (§8).

Недоступный корень, сбой чтения базы, отказ в доступе — запись в журнал, запуск продолжается; очистка идемпотентна. Старт ждёт её не дольше `CLEANUP_STARTUP_WAIT` = 5 с (лаунчер ждёт готовности backend 40 с, а недоступный сетевой диск может отвечать десятки секунд); остаток идёт в фоне и не трогает папки загрузок, начатых за это время (общий канонический ключ папки — `realpath` каталога, поэтому symlink, junction, `subst` и сетевой диск `Z:\` → UNC не мешают их узнать).

### 3.5. Завершение приложения

В `lifespan` при остановке: 1) новые загрузки не принимаются; 2) идущие и ждущие отменяются (`code: "shutdown"`); 3) ожидание их конца — запись в потоке закончена, файлы закрыты, `.part` удалены; 4) только потом закрываются резолвер, `app.state.http`, `app.state.hls_http` и остальное, как раньше. Ожидание ограничено `SHUTDOWN_WAIT` = 6 с — меньше 8 с, которые лаунчер ждёт остановки backend. Задачи, оставшиеся «активными» после аварийного падения запуска (сторож лаунчера поднимает backend в том же процессе), помечаются `cancelled/shutdown` и не опрашиваются интерфейсом вечно. Следующий запуск показывает готовые загрузки и не считает недокачанные успешными (`.part` не индексируются и удаляются).

### 3.6. Интерфейс

Без редизайна: те же кнопка, значки и стили.

- Кнопка идущей загрузки больше **не отключается** (`paintDl` ставил `disabled`, что убирало её и из обхода клавиатурой): крестик и этап/процент, нажатие отменяет. Доступное имя начинается с этапа и называет действие: «Скачивание: 40%. Нажми, чтобы отменить загрузку».
- «В очереди: начнётся, когда закончится одна из текущих загрузок» — приглушённо, без процента: не путается с передачей данных.
- Пока POST не подтверждён backend, кнопка `aria-disabled` («Подготовка… Загрузка запускается») — двойной клик не отменяет только что начатую загрузку. Пока запрос отмены в пути — «Загрузка отменяется…», фокус остаётся на кнопке.
- После отмены: «Загрузка «…» отменена», кнопка снова «Скачать», повтор работает. Опоздавшая отмена: «уже сохранён — отменить не успели», кнопка «Скачано». Прерывание перезапуском backend сообщается один раз.
- Меню «⋯»: «Отменить загрузку» / «Загрузка запускается…».
- «Скачанные»: «Скачано: N · загружается: A · в очереди: Q».
- Остальные экраны не изменились: `tests/ui_snapshots.py` capture/compare `96df026` против S11 — 76/76 (§5.1).

## 4. Совместимость

- Политика скачивания S5/S8 не менялась: скачивается штатный поток плеера (прогрессивный или HLS), без обходов DRM, авторизации, платного доступа и антибот-защиты. Тексты и машинные коды ошибок прежние.
- Сбой текстов или обложки по-прежнему не отменяет аудио.
- Формат папки (`audio.*`, `cover.*`, `lyrics.json`, `metadata.json`), индекс SQLite, локальное воспроизведение и уже скачанные файлы — без изменений (все прежние тесты загрузок, путей N3, локального воспроизведения и перезапуска проходят без правок).
- Контракт API только дополнен: состояния `queued`, `cancelled`, коды `cancelled`, `shutdown`, `shutting_down`, `no_job`, маршрут отмены. Интерфейс до S11 неизвестные состояния показывает как «Скачать».

## 8. Нерешённые риски и ограничения

- **WIN-14 — PASS по подтверждению владельца (19/19, 2026-10-16).** Владелец сообщил, что ручная проверка по [чек-листу](../checklists/S11_WINDOWS_CHECK.md) прошла успешно. Ограничение длинных путей остаётся: если в Windows выключены длинные пути (LongPathsEnabled = 0), сохранение в каталог с путём длиннее ~260 символов заканчивается понятной ошибкой; префикс `\\?\` не вводился.
- **TOCTOU на Windows сужен, но не закрыт.** Между повторной сверкой каталога и `unlink` локальный процесс, специально подменяющий папки в каталоге загрузок junction-ом, теоретически может перенаправить удаление файлов верхнего уровня; на SMB/FAT номер файла бывает 0, и сверка ничего не даёт. Полное решение — дескриптор каталога с `FILE_FLAG_OPEN_REPARSE_POINT` и удаление через `SetFileInformationByHandle` (ctypes) — отложено как несоразмерное угрозе (нужен локальный вредоносный процесс с правами пользователя).
- Если фоновая очистка «висит» на недоступном сетевом диске ровно на `.part` трека, который пользователь качает снова, загрузка ждёт в «Подготовке» (отмена работает). `_live_parts`/`_cleaning` — уровня процесса; после аварийного падения цикла ключи могут остаться до перезапуска процесса.
- Зависшая запись на диск (сетевой диск) держит завершение backend; верхняя граница — 8 с лаунчера и `os._exit`, остаток `.part` уберёт следующий старт.
- Каталог по умолчанию не чистится у пользователя с постоянным `WAVE_DATA_DIR` (переносной профиль), если там нет готовых загрузок Wave (иначе его покрывают проверенные корни).
- Нестабильный тест S10 на Windows CI (§6.1) — не исправлялся (посторонний код).
- TARGET_ARCHITECTURE §9 не обновлялся (задание ограничило правки документации ROADMAP и TEST_STRATEGY); фактическое состояние — в этом отчёте и ROADMAP.
